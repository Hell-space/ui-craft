工作原理

每次查询，
都是一次钻探。

从上往下穿过四层。越往下，数据越重，读得越少：前两层在内存里把 10 亿条缩到一千来个候选，后两层才去碰 NVMe。

  1. 01路由层内存

    从 104 万个分区里挑出 64 个

    查询向量先和 1,048,576 个质心比距离，只保留最近的 64 个分区。其余 99.99% 的数据，这次查询不会碰到。质心表常驻内存，只有 3.2 GB。

    0.4ms

  2. 02码本层内存

    用 64 字节的压缩码粗排

    64 个分区里共 61,056 条向量。每条只读它 64 字节的 PQ 压缩码来估算距离，留下最近的 1,024 条，作为下一步走图的起点。10 亿条压缩码共 64 GB，全部在内存。

    4.7ms累计 5.1 ms

  3. 03图层NVMe

    沿邻接图走到真正的近邻

    从这些起点出发，在邻接图上走 4 到 6 跳。每跳从 NVMe 读一页 4 KB 的邻接表，读请求成批并行发出：1,912 次随机读，7.3 毫秒。整张图 128 GB，最热的 48 GB 缓存在内存里。

    7.3ms累计 12.4 ms

  4. 04向量层NVMe

    取回原始向量，精排出前 10 条

    最后从 NVMe 取回 320 条 fp16 原始向量，算精确距离，返回前 10 条。1.54 TB 的原始向量只在这一步被读到，每次查询只读 480 KB。

    5.4ms累计 17.8 ms

接入

十来行代码，
接进你的 RAG。

  • 过滤在走图时生效

    lang = 'zh' 这类条件在遍历邻接图时就排除不符合的点，不是先召回 100 条再丢掉 90 条。带过滤的召回率@10 仍有 94.1%。

  • 写入 2 秒后可查

    新文档、新上架的商品先进内存层，后台合并到 NVMe。不用等夜里全量重建。

  • LangChain 与 LlamaIndex 现成可用

    两个 VectorStore 适配包随 0.9 发布，改一行初始化就能换掉原来的存储。

rag_search 
from strata import Client

db   = Client("http://localhost:7700")
docs = db.create_collection("support_docs", dim=768, metric="cosine")

# 写入后约 2 秒可查
docs.upsert(ids=ids, vectors=embeddings, payload=metadata)

hits = docs.search(
    vector=embed("二手手机拆封后还能退吗"),
    top_k=10,
    filter="lang = 'zh' AND updated_at > '2026-01-01'",
)
curl -X POST localhost:7700/v1/collections/support_docs/search \
  -H 'Content-Type: application/json' \
  -d '{
    "vector": [0.0132, -0.0871, 0.0419, ...],
    "top_k": 10,
    "filter": {"lang": "zh", "updated_at": {"gt": "2026-01-01"}}
  }'

# → {"hits": [{"id": "faq-2291", "score": 0.8817, ...}], "took_ms": 6.4}

适不适合

什么时候
不该用 Strata

单机是它的长处，也是它的边界。下面这几种情况，换一个工具会更省事。

适合

  • 1 亿到 30 亿条向量，想用一台机器扛住

    RAG 的文档切片库、推荐系统的商品与内容向量。

  • 在线召回要求 p99 稳定在 20 ms 以内

    NVMe 读取成批并发，不会因为一次缓存未命中拖出长尾。

  • 检索要带元数据过滤

    租户、语言、价格区间、更新时间，过滤后召回率不塌。

先别用

  • 不到 1,000 万条

    内存索引就放得下。改用 pgvector 或进程内的 HNSW 库，少运维一个服务。

  • 需要跨机房的强一致写入

    0.9 是单机加异步副本，主节点故障时会丢最后几秒的写入。

  • 持续写入超过每秒 5 万条

    写入会排队进内存层。分片写入在 1.0 的路线图里，预计 2027 年第一季度。
